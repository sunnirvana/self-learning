第 01 课 · 软件设计 → Agent

仅仅能工作是不够的

Ousterhout 说软件设计有两种工作方式。它们做的是同一类事——改系统、加功能——但首要目标相反。这个区分，可以直接用来看你怎么用 agent。

这节课你要带走的只有一句：这次优化的是「当前能跑」，还是「以后更好改」？能对一次编码、一次 agent 操作立刻做出判断，这节就完成了。

先把名字说准

你听到的「战术性设计 / 战略性设计」，在原书里叫战术式编程和战略式编程。它们不是两个层次、也不是两种架构风格，而是同一次工作里的两种心态。John Ousterhout，《A Philosophy of Software Design》第 3 章；讲义 Working Isn't Good Enough。

首要目标不同

战术式编程

首要目标
让下一项功能或下一个 bug 能工作。
允许什么
捷径、补丁、一点点额外复杂度——只要这次快。
结果
设计变差，复杂度升高。

战略式编程

首要目标
做出好设计，它碰巧也能工作。
真正在问
这段代码以后好不好演进？
做法
持续做小额投资，而不是一次设计完整个系统。
成为好设计师的第一步，是意识到仅仅能工作的代码是不够的。 Ousterhout，第 3 章

战术为什么会输

每一次捷径单独看都合理：截止时间在那儿，先让它跑起来。Ousterhout 的关键观察是：复杂度是增量的——不是某一个大错，而是几十、几百个小依赖和小隐晦堆出来的。堆到一定程度，清理要几个月，日程负担不起，于是继续打补丁。复杂度的精确定义（变更放大、认知负荷、未知的未知）下一课再练。本课只需要记住：它是一点点堆的，堆上就很难拆。

投资多少，投在哪

不是瀑布：不要企图一次设计完整个系统。系统会演化，第一次也设计不对，需求会变。正确做法是持续的小额投资，他给的量级是大约 10%–20% 的开发时间。讲义原话：as much as you can afford；10–20% overhead；投资大约 6–12 个月回本。

  • 主动投资：多花一点时间找更简单的设计，写清楚，想象系统可能往哪变。
  • 被动投资：发现设计错了，不要再打一层补丁，花额外时间修好。

10%–20% 够小，不至于把日程打爆；够大，几个月后速度会反过来。到那时，过去的投资省下的时间，就能覆盖以后的投资。

战术式飓风

几乎每个组织都有至少一位把战术式编程发挥到极致的人：出活极快，管理层眼里的英雄，留下一串别人必须收拾的乱摊子。真正的英雄往往显得更慢——因为他们在还债。原词 tactical tornado。中文常用「战术式飓风」。见第 3 章。

迁到 agent：同一根尺子

类比 · 不是原书内容

Ousterhout 没写过大模型。下面是把同一把尺子挪到 agent 上，要用你自己的使用来检验。

把「系统」看成两层：agent 正在改的代码，以及 agent 自己的工作方式（提示、技能、工具、记忆、约定）。战术式优化的是这一次对话的答卷；战略式优化的是下一次同类任务还好不好做。

战术式用 agent

提示能跑就交差。失败了就把日志整段贴回去。系统提示里越堆越多「注意不要……」。多开几个会话撞运气。

战略式用 agent

抽出可复用的技能。删掉一条制造隐晦的指令。把这次踩坑变成以后默认会避开的约定。主动拿出大约一到两成时间，改善 agent 的接口，而不只是追加提示。

Agent 里的「战术式飓风」长这样：特别能出活——并行很多会话、上下文塞得满满——但技能文件、工具和约定乱到你自己都不敢再交给它一件稍大的事。

练：先分类，再回忆

先判断下面四件事是战术式还是战略式。对了、错了都会立刻看到理由。选项字数相同，不要靠长短猜。

场景 2 / 4 · 代码

今天就能用

下一次驱动 agent 之前，先问自己：我这 10%–20% 的精力，要花在改善系统上，还是只花在催这一次出结果？改善系统的最小动作通常是：抽一条技能、删一条含糊指令、把一个隐晦的失败变成明确约定。

把最近一次真实用法带回给老师。贴一段你怎么用 agent 的过程（或一段你刚写的代码决策）。我会按这节的尺子标：战术式还是战略式，留下的是投资还是复杂度。任何一句不清楚的，直接问。
