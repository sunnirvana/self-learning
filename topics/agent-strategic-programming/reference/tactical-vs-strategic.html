战术式编程 vs 战略式编程

Ousterhout 第 3 章的压缩版。判断时只问首要目标：当前能跑，还是以后更好改。

战术式编程

首要目标
让下一项功能或 bug 能工作。
允许
捷径和补丁，只要这次快。
留下什么
增量复杂度：小依赖 + 小隐晦。
短期
更快。
几个月后
越改越慢。

战略式编程

首要目标
好设计，碰巧也能工作。
真正在问
以后好不好演进？
留下什么
对系统的小额投资。
短期
慢大约 10%–20%。
几个月后
投资回本，之后的投资接近免费。

投资

  • 量级：大约 10%–20% 的开发时间，持续，不是瀑布。
  • 主动：多花时间找更简单的设计；写清楚；预想可能的变化。
  • 被动：发现设计问题就修，不打第二层补丁。
  • 不能一次设计完整个系统；第一次也对不准；需求会变。

战术式飓风

出活极快、常被当成英雄、留下别人必须收拾的乱摊子。还债的人显得更慢。

一句判断

这次优化的是「当前能跑」，还是「以后更好改」？

一次做完之后

  • 产出满意仍可能是战术式：下次还要重写 prompt，系统就没有更好改。
  • 第一次从零写可以（设计第一次很难对）。看见重复还不抽，才是继续战术式。
  • 最小投资：切开「下次仍为真的方法」和「只属于这一次的实例」。
  • 整份对话存档不是投资，是残留。

方法卡片五栏：何时用 / 每次另给的输入 / 每次应得到的产出 / 步骤 / 不要。详见 第 02 课。

迁到 agent（类比，非原书）

类比 · 不是原书内容

系统有两层：agent 正在改的代码，以及 agent 自己的工作方式（提示、技能、工具、记忆、约定）。

战术式

催这一次答卷：整段贴日志、追加「不要……」、多开会话撞运气、提示能跑就交。

战略式

改善以后还能用的接口：抽技能、删含糊指令、把隐晦失败变成约定。拿出大约一到两成时间做这件事。
